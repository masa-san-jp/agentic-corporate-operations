# AIエージェントによって究極まで自動化された事業会社のノンプロフィット領域
## 理想オペレーティングモデル・要求仕様・プロトコル

作成日: 2026-07-29  
文書種別: 参照アーキテクチャ / 要求仕様  
対象: 事業会社の非収益部門、間接部門、統制部門、経営支援部門

---

## 0. 結論

究極の自動化とは、単に人員を削減することではない。

> **人間が「目的、価値、許容リスク、不可逆な意思決定」を定め、AIエージェントが「発見、分解、実行、検証、記録、改善」を継続的に完了する組織である。**

理想状態では、業務は担当者の受信箱、記憶、会議、口頭指示によって動かない。すべての業務が構造化された `Work Object` として登録され、方針・権限・証拠・完了基準に基づいて自律処理される。

人間が介入するのは次の4種類に限定する。

1. 目的・方針・予算・リスク許容度の設定
2. 法的、倫理的、社会的に不可逆な判断
3. 複数の正解があり、価値選択を要する判断
4. 既存ルールでは処理不能な新規例外の規範化

それ以外は、原則としてAIエージェントが完了まで処理する。

---

## 1. 対象範囲の定義

本書でいう「ノンプロフィット領域」とは、売上を直接計上する事業活動ではなく、次の機能を指す。

- 経営の方向を定める
- 資源を配分する
- 業務を成立させる
- 法令・規程・契約を守る
- リスクを管理する
- 記録と証拠を残す
- 人、資金、情報、設備を維持する
- 事業継続性を確保する
- 組織学習を蓄積する

営業、商品提供、顧客対応等のプロフィット領域との境界は「売上への直接寄与」ではなく、**最終成果物の受益者と責任主体**で判断する。例えば、価格決定は経営管理、請求処理は財務、顧客契約の締結は法務統制を含むため、複数領域にまたがる。

## 2. 理想系の機能分類

### 2.1 11の機能領域

| ID | 機能領域 | 主目的 | 理想的な自動化状態 |
|---|---|---|---|
| G01 | 経営ガバナンス・意思決定 | 目的、方針、権限、重要意思決定の統制 | 会議ではなく構造化された意思決定案件として処理 |
| G02 | 戦略・予算・ポートフォリオ | 資源配分と優先順位最適化 | 実績・予測・制約から配分案を常時再計算 |
| G03 | 財務・会計・税務・資金 | 正確な記録、決算、資金維持 | 取引発生から仕訳、照合、予測、報告まで例外駆動 |
| G04 | 法務・契約・コンプライアンス | 法的義務・契約義務・倫理基準の遵守 | 義務を機械可読化し、全業務を継続検査 |
| G05 | リスク・内部統制・内部監査 | 目的達成を阻害するリスクの管理 | 全取引・全プロセスを常時監査し、証跡を自動生成 |
| G06 | 人事・労務・組織 | 人的資源の配置、維持、育成 | 人事イベントを起点に必要処理を自動連鎖 |
| G07 | 調達・購買・ベンダー・資産 | 外部資源の適正取得と維持 | 需要発生から比較、契約、検収、支払、更新まで統合 |
| G08 | IT・データ・AI・情報セキュリティ | デジタル基盤と情報資産の維持 | ID、端末、権限、システム、AIをポリシー駆動で運用 |
| G09 | ナレッジ・文書・記録管理 | 組織知と証拠の保存・再利用 | すべての活動から知識を抽出し、再利用可能に更新 |
| G10 | 総務・施設・BCP・インシデント | 物理的・運用的な事業継続 | 異常検知から代替運用、復旧、事後改善まで自動化 |
| G11 | 経営秘書・社内コミュニケーション | 経営者と組織の認知負荷低減 | 必要情報だけを適時に提示し、指示を業務へ変換 |

### 2.2 横断機能

11領域とは別に、全領域を貫く6つの共通機能を設ける。

1. **Task Curator**: 曖昧な依頼を実行可能な仕事へ変換
2. **Policy Engine**: 法令、規程、契約、権限、リスク許容度を判定
3. **Orchestrator**: 複数エージェント、システム、人間を編成
4. **Evidence Engine**: 根拠、入力、処理、出力、承認、変更履歴を保存
5. **Exception Manager**: 停止、失敗、矛盾、期限超過を収束
6. **Learning Engine**: 実行結果から手順、ルール、評価器を改善

## 3. 全体構造

### 3.1 8層アーキテクチャ

```text
[1. Purpose Layer]
  経営目的 / KPI / リスク許容度 / 価値基準
          ↓
[2. Policy Layer]
  法令 / 社内規程 / 契約 / 権限 / 予算 / 禁止事項
          ↓
[3. Work Intake Layer]
  メール / Chat / Calendar / Form / API / センサー / 定期イベント
          ↓
[4. Task Curator Layer]
  分類 / 正規化 / 分解 / 優先順位 / 完了基準 / リスク判定
          ↓
[5. Agent Execution Mesh]
  専門エージェント / 検証エージェント / 監査エージェント
          ↓
[6. Tool & Data Plane]
  ERP / 会計 / HRIS / GWS / CRM / 銀行 / 電子契約 / Git / DWH
          ↓
[7. Evidence & Control Plane]
  ログ / 証跡 / 評価 / 承認 / 差分 / 例外 / インシデント
          ↓
[8. Learning & Improvement Layer]
  再発防止 / SOP更新 / ポリシー候補 / 自動化拡張 / 廃止
```

### 3.2 単一の業務単位: Work Object

すべての業務は、最低限次の属性を持つ。

```yaml
work_id: 一意識別子
work_type: 業務種別
source: 発生源
purpose: 達成すべき成果
requested_output: 成果物
acceptance_criteria: 完了基準
deadline: 期限
priority: 優先度
risk_class: リスク区分
reversibility: 可逆性
authority_required: 必要権限
policy_refs: 適用方針
inputs: 入力データ
dependencies: 先行条件
assigned_agents: 実行主体
next_action: 次の具体的行動
status: 状態
evidence_refs: 証跡
exception_code: 停止理由
review_mode: 検証方法
retention_class: 保存区分
```

**禁止状態**

- 所有者または担当エージェントが不明
- 次の行動が不明
- 完了基準がない
- 停止理由が自由記述のみ
- 期限超過が通知されない
- 実行結果に根拠がない
- 外部送信・支払・契約に権限記録がない

## 4. 自律度の定義

| レベル | 状態 | 人間の関与 |
|---|---|---|
| A0 | 手動 | 人間が判断・実行・検証 |
| A1 | 支援 | AIが案を作成、人間が実行 |
| A2 | 承認後実行 | AIが計画、人間が承認、AIが実行 |
| A3 | 自律実行・事後確認 | 規程内でAIが実行、一定割合を事後レビュー |
| A4 | 例外駆動 | AIが完結し、例外時のみ人間介入 |
| A5 | 自己改善型 | AIが手順・評価器・分業構造まで改善 |

### 理想的な適用

- 定型・可逆・低影響業務: A4
- 金銭支払、雇用条件変更、対外公表: A2〜A3
- 解雇、訴訟方針、重要契約、資本配分: A1〜A2
- 方針、倫理、リスク許容度、権限体系変更: 人間専管
- SOP改善、分類器改善、プロンプト改善: A5。ただし本番反映はリスク区分に従う

**A5は無制限自律ではない。**  
AIが変更できるのは、事前に定義された変更可能領域だけである。憲法、価値基準、法的責任、権限上限は自動変更させない。

## 5. 共通要求仕様

### 5.1 機能要求

全領域は次を満たさなければならない。

1. すべての業務発生源を自動収集できる
2. 非構造入力をWork Objectへ正規化できる
3. 業務を有限なタスクへ分解できる
4. 適用法令、規程、契約、権限を特定できる
5. 完了条件を実行前に確定できる
6. 外部システムをAPIまたはRPAで操作できる
7. 実行結果を独立した評価器で検証できる
8. 失敗時に再試行、代替経路、停止、エスカレーションを選択できる
9. すべての処理に再現可能な証跡を残せる
10. 実行結果をナレッジと管理指標へ反映できる

### 5.2 非機能要求

| 項目 | 必須要件 |
|---|---|
| 可用性 | 重要度別にSLOを定め、停止を自動検知する |
| 冪等性 | 同じ処理を再実行しても二重支払・二重登録が発生しない |
| 再現性 | 同一の入力、ルール版、モデル版から結果を追跡できる |
| 説明可能性 | 判断理由、参照情報、適用ルールを提示できる |
| 可観測性 | 成功、失敗、滞留、コスト、品質を常時監視できる |
| セキュリティ | 最小権限、職務分離、秘密管理、改ざん防止を実装する |
| プライバシー | 利用目的、データ最小化、保持期限、削除を管理する |
| ベンダー独立性 | モデル、SaaS、実行基盤を交換可能にする |
| コスト統制 | 1件当たり処理費、モデル費、外部API費を測定する |
| 品質保証 | 正解率だけでなく、重大誤り率と見逃し率を管理する |

### 5.3 内部統制要求

- 起案、承認、実行、検証の役割を論理的に分離する
- 同一エージェントが自分の出力を唯一の根拠として承認しない
- 権限は個人名ではなくロールと条件で付与する
- 支払、契約、個人情報、対外送信には追加制御を設ける
- 監査ログは実行エージェントから変更不能にする
- 重要ルール変更は差分、影響分析、承認、ロールバック手段を必須とする
- 例外処理は通常処理より強い証跡を残す
- 緊急権限は期限付きとし、事後レビューを必須とする

## 6. 領域別の理想系

## G01. 経営ガバナンス・意思決定

### 目的

経営判断を会議、口頭、記憶から切り離し、再現可能な意思決定プロセスにする。

### 構造

- Decision Registry: 全重要意思決定の台帳
- Authority Matrix: 決裁権限
- Policy Repository: 方針・規程
- Board Agent: 取締役会資料生成
- Challenge Agent: 反証・反対意見生成
- Decision Auditor: 手続、根拠、利益相反の検査

### 標準プロセス

1. 論点をDecision Objectとして登録
2. 目的、選択肢、制約、期限を確定
3. 必要情報を自動収集
4. 選択肢別の効果、リスク、不可逆性を算定
5. 反証エージェントが前提を攻撃
6. 権限者が価値判断を行う
7. 決定、根拠、反対意見、条件を記録
8. 実行タスクへ分解
9. 期限後に結果を検証

### 完了基準

- 決定者と権限根拠が特定されている
- 選択肢を最低2案比較している
- 反対論と主要リスクを記録している
- 決定後の担当、期限、測定指標がある
- 結果レビュー日が設定されている

### 自律上限

AIは推奨案まで。目的、価値配分、重大な不可逆判断は人間が決定する。

---

## G02. 戦略・予算・ポートフォリオ

### 目的

予算編成を年1回の政治的交渉から、継続的な資源配分へ変える。

### 必要データ

- 事業KPI
- PL、BS、CF
- 人員・稼働
- プロジェクト進捗
- 契約・固定費
- リスク・規制
- 資本制約
- 経営目標

### 標準プロセス

1. 目標を測定可能な成果へ変換
2. 現状との差を算定
3. 施策候補を収集
4. 費用、効果、確度、期間、依存関係を評価
5. 制約条件下で配分案を生成
6. シナリオ比較
7. 権限に応じて承認
8. 予算・人員・タスクを配賦
9. 実績に応じて予測と配分を更新

### 完了基準

- すべての予算が目的または義務に紐づく
- 無目的な継続費用がない
- 施策ごとに撤退条件がある
- 予測差異に原因分類がある
- 変更前後の資源配分が追跡できる

### 目標状態

月次予算ではなく、日次または週次で更新されるRolling Forecastを基本とし、人間は配分原則と例外のみ判断する。

## G03. 財務・会計・税務・資金

### 目的

取引発生から決算・資金予測までを一つのイベント連鎖にする。

### エージェント構成

- Transaction Ingestion Agent
- Accounting Classification Agent
- Reconciliation Agent
- Closing Agent
- Treasury Agent
- Tax Obligation Agent
- Fraud Detection Agent
- Financial Reporting Agent

### 標準プロセス

1. 請求書、領収書、銀行、契約、注文、検収を取得
2. 取引主体、日付、金額、税区分、部門、勘定を推定
3. 契約・発注・検収との三点照合
4. 異常、重複、欠損を検出
5. 仕訳案または自動仕訳
6. 入出金予定と資金繰りを更新
7. 月次締めの未処理項目を自動回収
8. 決算資料、差異分析、注記候補を生成
9. 税務論点を分類し、申告資料を作成

### 必須統制

- 支払先変更は独立確認
- 新規口座、例外支払、閾値超過は追加承認
- 仕訳生成と承認を分離
- 銀行データと帳簿を日次照合
- 証憑と仕訳を双方向リンク
- 税務判断の根拠条文・解釈・前提を保存

### 完了基準

- 未照合取引ゼロ、または理由付き例外
- 証憑欠損ゼロ、または回収タスク化
- 二重計上・二重支払がシステム上防止される
- 月次締めの全タスクに状態と証拠がある
- 資金不足予測が事前警告される

### 自律上限

通常仕訳、照合、定型支払はA4。高額支払、口座変更、税務見解、新規会計方針はA2以下。

## G04. 法務・契約・コンプライアンス

### 目的

法令・契約義務を文書保管から、実行時に機能する機械可読ルールへ変える。

### 構造

- Obligation Registry: 法令・契約・許認可・届出義務
- Clause Library: 標準条項
- Contract Lifecycle System
- Compliance Rule Engine
- Regulatory Change Agent
- Legal Issue Escalation Queue

### 標準プロセス

1. 法令、ガイドライン、契約、社内規程を収集
2. 義務、禁止、期限、対象、証拠を構造化
3. 業務・取引・データ処理と対応付け
4. 変更を検知し影響範囲を特定
5. 契約案を標準条項と比較
6. リスク条項を抽出
7. 権限に応じて修正、承認、締結
8. 契約後の義務、更新、解約、報告をタスク化
9. 違反兆候を継続監視

### 完了基準

- すべての契約に責任部門、更新日、解約条件がある
- 義務に実行タスクと証拠が紐づく
- 規制変更に影響判定がある
- 標準外条項に理由と承認がある
- 期限徒過が通知なしで発生しない

### 自律上限

標準契約はA3〜A4。非標準責任、訴訟、行政対応、権利放棄はA1〜A2。

---

## G05. リスク・内部統制・内部監査

### 目的

年次監査から、全業務を対象にした常時保証へ移行する。

### 構造

- Risk Register
- Control Library
- Process Graph
- Continuous Control Monitoring
- Audit Evidence Store
- Independent Audit Agent

### 標準プロセス

1. 目的とプロセスを特定
2. 失敗モードとリスクを抽出
3. 予防、発見、是正統制を割り当て
4. 統制をシステム上で自動実行
5. 全件検査または高リスク優先検査
6. 逸脱を検知
7. 是正措置を発行
8. 再発防止を検証
9. 残余リスクを経営へ報告

### 完了基準

- 重大プロセスに未評価リスクがない
- 重要統制に実施証拠がある
- 例外に原因、責任、期限、是正策がある
- 同一原因の再発が識別される
- 監査対象がサンプリングだけに依存しない

### 独立性要件

実行エージェントと監査エージェントは、モデル、プロンプト、権限、ログの少なくとも一部を分離する。監査側は実行結果を変更できず、実行側は監査記録を削除できない。

---

## G06. 人事・労務・組織

### 目的

採用、入社、配置、評価、勤怠、育成、退職をイベント駆動で接続する。

### 主なイベント

- 採用申請
- 応募
- 内定
- 入社
- 異動
- 昇降格
- 休職
- 復職
- 契約更新
- 退職
- 労務異常
- 組織変更

### 標準プロセス

1. 人員需要を事業計画から算出
2. 採用要件を職務成果と能力へ分解
3. 候補者情報を収集・評価
4. 面接記録を構造化
5. 入社決定後、契約、アカウント、端末、研修を連鎖実行
6. 勤怠、負荷、配置、成果を継続監視
7. 評価資料を証拠から生成
8. 育成施策を割り当て
9. 退職時に権限、資産、知識移管を回収

### 必須統制

- 差別につながる属性を評価根拠に使用しない
- 人事評価に使用したデータとロジックを記録
- 給与、懲戒、解雇は人間承認
- 個人情報は目的別・最小権限
- センシティブな推定を原則禁止
- AIによる評価は異議申立て経路を設ける

### 完了基準

- 入退社に伴う未処理アカウント・資産ゼロ
- 雇用条件と給与計算条件が一致
- 人事判断に根拠と承認がある
- 勤怠異常が放置されない
- 退職者のアクセスが期限内に停止される

---

## G07. 調達・購買・ベンダー・資産

### 目的

要求、比較、契約、検収、支払、更新、廃棄を一つのライフサイクルとして管理する。

### 標準プロセス

1. 需要を検出
2. 既存在庫・既契約・代替手段を確認
3. 仕様と評価基準を確定
4. 候補ベンダーを収集
5. 価格、品質、継続性、セキュリティ、法務を評価
6. 発注・契約
7. 納品・検収
8. 支払
9. 利用率・品質・SLAを監視
10. 更新、再交渉、解約、廃棄

### 完了基準

- 発注前に予算・権限・必要性を確認
- 重要ベンダーに代替手段がある
- 契約と実利用が照合される
- 未使用ライセンスを検出する
- 更新前に継続妥当性を再評価する
- 資産の所在、利用者、状態、廃棄証拠が追跡可能

### 自律上限

カタログ購買はA4。新規重要ベンダー、長期拘束、高額契約はA2。

## 7. 共通業務プロセス

すべての領域は次の有限状態機械で動作する。

```text
CAPTURED
  → CLASSIFIED
  → SPECIFIED
  → PLANNED
  → AUTHORIZED
  → EXECUTING
  → VERIFYING
  → COMPLETED
```

例外状態:

```text
BLOCKED
WAITING_EXTERNAL
RETRYING
ESCALATED
CANCELLED
FAILED
```

### 7.1 各状態の退出条件

| 状態 | 次へ進む条件 |
|---|---|
| CAPTURED | 発生源、依頼内容、対象が保存された |
| CLASSIFIED | 業務種別、重要度、リスク区分が決まった |
| SPECIFIED | 成果物、期限、完了基準、制約が確定した |
| PLANNED | 有限な実行手順、依存関係、担当が決まった |
| AUTHORIZED | 必要な権限、予算、承認が揃った |
| EXECUTING | 各ステップが実行され、結果が保存された |
| VERIFYING | 独立評価で完了基準を満たした |
| COMPLETED | 成果物、証跡、通知、知識反映が完了した |

**時間経過だけで状態を進めてはならない。**  
各状態は証拠によってのみ遷移する。

## 8. 標準プロトコル

## P01. Intake Protocol

入力チャネルを問わず、受信時に次を実行する。

1. 原文保存
2. 発信者と権限確認
3. 依頼、情報、決定、相談、通知に分類
4. 重複検出
5. 期限・金額・対象・依存関係抽出
6. Work Object生成
7. 不足情報を推定可能・照会必須に分ける
8. 受付通知

## P02. Task Curation Protocol

1. 目的を成果物に変換
2. 成果物を検証可能な条件へ変換
3. 依存関係を特定
4. 1ステップを一つの実行主体で完了可能にする
5. 最大実行時間を設定
6. 失敗時の代替経路を設定
7. 終了条件を設定
8. リスクと権限を判定

**分解終了基準**

- 各タスクに明確な入力と出力がある
- 実行可否をYes/Noで判定できる
- 完了を機械的に検査できる
- 未知の探索に時間または回数上限がある

## P03. Policy Decision Protocol

1. 対象事実を確定
2. 適用ルール候補を検索
3. 優先順位を判定
4. 義務、禁止、裁量を分離
5. 矛盾を検出
6. 判定と確信度を出力
7. 閾値未満は人間へエスカレーション
8. 参照ルール版を保存

## P04. Execution Protocol

1. 前提条件確認
2. 権限トークン発行
3. 一意の実行キー生成
4. 実行
5. 結果取得
6. 期待値との差分確認
7. 証跡保存
8. 次のステップへ遷移

## P05. Verification Protocol

検証は最低3層で行う。

- **構文検証**: 必須項目、形式、型
- **意味検証**: 内容の整合性、計算、根拠
- **業務検証**: 目的、規程、権限、実世界の結果

高リスク業務は追加で独立エージェントまたは人間が検証する。

## P06. Exception Protocol

停止したWork Objectは放置しない。

```yaml
exception_code:
cause:
detected_at:
impact:
retryable:
retry_count:
next_retry_at:
fallback:
human_role_required:
escalation_deadline:
closure_condition:
```

処理順序:

1. 自動再試行
2. 代替ツール・代替データ
3. タスク再分解
4. 依存先への自動督促
5. 権限者への選択式エスカレーション
6. 期限超過時の上位エスカレーション
7. 中止または方針変更
8. 原因を再発防止へ反映

**禁止事項**: 「確認待ち」「対応中」「保留」だけで停止させない。

## P07. Human Escalation Protocol

人間への照会は自由記述質問ではなく、原則として次の形式にする。

```yaml
decision_required:
recommended_option:
alternatives:
evidence:
risk_if_approved:
risk_if_rejected:
deadline:
default_action_if_no_response:
authority_basis:
```

人間は長文を読み直さず、判断のみ行える状態にする。

## P08. Change Protocol

1. 変更要求
2. 影響分析
3. テストケース生成
4. サンドボックス試験
5. 回帰評価
6. リスク判定
7. 承認
8. 段階展開
9. 監視
10. ロールバックまたは正式化

対象は、SOP、プロンプト、モデル、ツール、API、権限、ルール、データスキーマを含む。

## P09. Evidence Protocol

1件の完了業務に対して最低限保存するもの:

- 原入力
- 使用データ
- 適用方針と版
- 実行計画
- 実行ログ
- 外部システム応答
- 検証結果
- 承認記録
- 成果物
- 通知記録
- 例外と再試行
- 使用モデル・プロンプト・ツール版

## P10. Learning Protocol

1. 成功率、時間、コスト、例外を集計
2. 反復例外をクラスタリング
3. 原因をデータ、ルール、ツール、権限、設計に分類
4. SOPまたは自動化変更案を生成
5. 過去案件でシミュレーション
6. 改善効果と新規リスクを評価
7. 承認後に段階導入
8. 効果がなければ自動撤回

## 9. リスク区分と人間関与基準

### 9.1 リスク評価軸

各業務を次の軸で0〜4点評価する。

- 金銭影響
- 法的影響
- 個人への影響
- 対外影響
- 情報機密性
- 不可逆性
- 検出困難性
- 事業継続影響

### 9.2 区分

| 区分 | 条件 | 原則 |
|---|---|---|
| R0 | 無影響・完全可逆 | A4 |
| R1 | 軽微・容易に検出可能 | A4、事後抽出レビュー |
| R2 | 中程度・限定的影響 | A3、独立検証 |
| R3 | 重大・個人/金銭/法務影響 | A2、人間承認 |
| R4 | 経営・社会・生命・重大権利影響 | A1、複数人承認または人間専管 |

### 9.3 強制的にR3以上とする行為

- 外部への送金
- 契約締結・解除
- 雇用条件の不利益変更
- 懲戒・解雇
- 個人情報の目的外利用
- 公的機関への正式回答
- 訴訟・紛争方針
- 外部公表
- 重要システムの本番停止
- 権限管理基盤の変更

## 10. 具体的な達成基準

以下は法令上の基準ではなく、理想系を評価するための設計目標である。

### 10.1 業務構造化

- 業務発生の95%以上が自動取得される
- 実行対象業務の100%にWork Objectがある
- Work Objectの100%に次アクション、期限、完了条件がある
- 自由記述のみの停止理由は0件
- 期限超過の未通知は0件

### 10.2 自動完了

- 低リスク定型業務の90%以上が人手なしで完了
- 中リスク業務の80%以上が承認以外を自動完了
- 人間が再入力するデータ項目を原則ゼロ
- 同一情報を複数システムへ手作業転記しない
- 定例報告資料の80%以上を自動生成

### 10.3 品質

- 重大誤処理率: 0.1%未満を目標
- 二重支払、二重登録、未承認契約: 0件
- 検証不能な完了: 0件
- 根拠のないAI判断: 0件
- 未解決の重大例外: 0件

### 10.4 統制

- 高リスク操作の100%に権限確認
- 高リスク操作の100%に独立検証
- 重要ルール変更の100%に回帰試験
- 全エージェント操作の100%に監査ログ
- 退職者・異動者の不要権限を規定時間内に100%削除

### 10.5 応答と滞留

- 受付から分類: 5分以内
- 低リスク定型業務の着手: 15分以内
- 外部待ち以外の停止を1営業日以内に解消または上申
- 人間判断待ちには期限とデフォルト動作を100%設定
- 例外の平均滞留時間を継続的に短縮

### 10.6 ナレッジ

- 重要意思決定の100%をDecision Registryに保存
- 重要SOPの100%に所有者、版、有効日、再確認日がある
- 引用可能な知識の100%に原典リンクがある
- 廃止ルールの本番参照を0件にする
- 反復3回以上の例外は必ず改善候補に登録する

### 10.7 経済性

- 業務種別ごとに1件当たり総処理費を算定
- 人手時間だけでなくAI、API、SaaS、監査コストを含める
- 自動化前後で処理時間、品質、統制、リードタイムを比較
- 自動化による新規管理コストが削減効果を上回る業務は廃止または再設計する

## 11. 人間組織の理想形

人間の役割は「作業担当」から次へ移行する。

| 人間ロール | 責任 |
|---|---|
| Purpose Owner | 目的、成果、優先順位を定義 |
| Policy Owner | 規程、判断原則、禁止事項を定義 |
| Risk Owner | 許容リスクと対応方針を決定 |
| Authority Holder | 不可逆・高影響な承認 |
| Exception Governor | 新規例外を一般ルールへ昇格 |
| System Steward | エージェント群の品質と変更を統制 |
| Independent Assurer | 独立監査・妥当性保証 |

日常業務の「担当者」は原則不要になる。残るのは、責任、規範、権限、保証を持つ役割である。

## 12. 会議の理想形

定例会議は情報共有の場ではなく、次のいずれかに限定する。

1. 新しい目的を定める
2. 方針間の矛盾を解消する
3. リスク許容度を変更する
4. 複数の価値が衝突する案件を判断する
5. 既存ルールで処理できない例外を規範化する

会議前にAIが次を完了する。

- 論点整理
- 事実確認
- 選択肢生成
- 影響分析
- 反対論生成
- 推奨案
- 未確定事項の限定

会議後は、決定を自動的に方針、タスク、予算、権限、通知へ反映する。

## 14. 導入時の優先順位式

自動化候補は、次の観点で評価する。

```text
Automation Priority
= Frequency
× Human Time
× Standardizability
× Error Cost
× Data Availability
÷ Implementation Risk
```

ただし、単純な工数削減だけで選ばない。次を優先する。

1. 停止すると全社が止まる業務
2. 事故・法令違反・支払誤りを防ぐ業務
3. 複数部門をまたぐ転記・照合作業
4. 期限管理が重要な業務
5. 同じ判断を反復する業務
6. 証拠作成負荷が高い業務

## 15. 最終的な理想状態

最終状態では、会社は次のように動く。

- 人間はやりたいこと、守るべきこと、許容できないことを定める
- AIが曖昧な要求を実行可能な業務へ変換する
- AIが必要情報を集め、計画し、実行する
- 別のAIが結果と統制を検証する
- 失敗は再試行、代替、上申のいずれかで必ず収束する
- すべての判断と処理に証拠が残る
- 同じ失敗が繰り返されると、仕組み自体が修正される
- 人間は処理件数ではなく、成果、連続性、価値、次の目的だけを評価する

究極のノンプロフィット部門は「管理部門」ではない。

> **会社の目的を、制約の中で、安全かつ継続的に実現する自律制御系である。**
